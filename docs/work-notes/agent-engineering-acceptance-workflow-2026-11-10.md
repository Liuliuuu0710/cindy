# Agent 工程优化验收流程

> 状态：可复用工作流程，2026-11-10；已结合 #9398 分阶段验收复盘更新。
> 本文是方法与模板；各案例是否执行，以对应验收记录为准。未设置自动化。
> 来源：用户提供的工程优化建议截图，以及本轮 PR 产品复盘。
> 本文用于组织一次可重复的验收，不新增仓库强制门禁，也不自动授权后续写操作。

## 目标与交付物

围绕一个真实问题，证明优化后用户能得到正确结果、失败能被解释和恢复、原有能力得到保留。
最终交付一份包含 **任务轨迹、失败分类、优化前后对比和未验证项** 的验收记录。

流程顺序：

**选定场景 → 固定需求与基线 → 核对调用链及已有覆盖 → 列验收矩阵 → 记录基线结果 → 单因素优化 → 同条件复验 → 人工审阅与收口。**

先完成只读分析。实现、故障注入、真实环境验证和自动化仅在相应工作获准后开展；当前文档中的步骤不表示已执行。
沿用[开发工作流](../dev-rules/development-workflow.md)的范围控制和三个需求核对点；新增测试遵守[工程约定](../dev-rules/engineering-conventions.md) §3.2。

## 1. 选定一个场景，固定需求与基线

执行人从一个真实 Issue 或原始任务开始；后续比较再扩展为固定的 5–10 个典型案例，不为凑数量新增重复用例。
初始候选是 #8611 对应的“回复生成后提交失败”；首个实际应用案例为
[#9398 分阶段验收](issue-9398-acceptance-2026-11-10.md)。选择已有修复时，工作目标可以是补验收，
不要求另写实现，也不将他人的修复算作本轮代码贡献。

开工卡必须填清：

| 字段 | 填写内容 |
| --- | --- |
| 原始目标 | 用户从哪个入口做什么，当前受阻现象，预期可观察结果 |
| 必须保留 | 正文、附件、过程入口、原交互、权限边界及适用的跨端行为 |
| 本次范围 | 包含/不包含的行为；只读分析、受控实验或真实环境验证 |
| 基线 | 仓库与提交、客户端构建、harness/模型版本与配置、相关服务版本；未知项明确标注 |
| 固定输入 | 案例编号、最小输入、初始状态、前置条件及可复用的脱敏夹具 |
| 判定与预算 | 通过条件、重复次数、时间/工具调用预算；性能目标须在比较前设定 |
| 责任与依据 | 执行人、结果审阅人、原需求和适用规则；关键产品取舍是否已有决定 |

**进入下一步的条件：**能明确判断用户是否得到预期结果。关键取舍有歧义时只暂停依赖该取舍的部分，其余只读定位继续。
不能把建议的实现方式当成必须实现的产品目标。

## 2. 核对执行链和已有覆盖

按以下链路查真实代码与测试，不凭通用流程猜测各 harness 的实现：

**用户输入 → 上下文与授权 → 模型/工具执行 → 结果提交 → 回执/读回 → 界面状态。**

每个环节记录：生产入口、输入来源、可观察输出、异常分支、已有测试位置、证据或未知项。
同时查后续修复与并行 PR，区分已有代码、已合并、版本包含、部署生效、现场验收五种状态。
已有实现覆盖的只补验收证据；缺证据不等于缺代码。

截图中的研究方向仅作候选，不视为本次已核验的缺陷或覆盖缺口：

| 候选案例 | 要核验的机制 | 查验重点 |
| --- | --- | --- |
| #8611 | 生成完成与交付完成的区别 | 幂等、回执不确定性、失败收尾、降级能力损失 |
| #8075 | 上下文与操作授权的区别 | 主人原话的核实来源、引用不能授权、撤权与历史恢复 |
| #9120 | 卡片与宿主生命周期 | 文档就绪、加载/重载、动作丢失与重复触发 |
| #8088 | 后续提交中的遗漏类型 | 多语言、同步主干和性能影响；不能仅凭提交次数判定无效返工 |

**产出：**调用链与覆盖清单。若无法取得实际实现或现场证据，注明缺失位置和获取方式，不填写推测性结论。

## 3. 在优化前列出验收矩阵

先写预期，再找已有覆盖；以下 #8611 场景均为待核验，不能直接据此新增测试。
故障只在受控夹具/隔离测试环境注入，不向生产服务人为制造断网、拒绝或重复写入。

| 编号 | 场景及注入位置 | 预期可观察结果 | 已有测试/缺失证据 | 当前结果 |
| --- | --- | --- | --- | --- |
| D0 | 无故障的正常提交 | 回复持久保存，读回与界面一致，过程入口及附件保留，执行状态正确 | 待核对实际入口及用例 | 未执行 |
| D1 | 服务端明确拒绝 complete 内容 | 仅命中现有受限兜底时重试；不重跑模型；正文及附件保留；去掉过程卡须记为降级 | 待核对确定拒绝的判据、同操作标识与去卡分支 | 未执行 |
| D2 | 服务端已成功保存，但回执丢失 | 结果保持未知直至核实；依既有协议查询或以相同幂等标识恢复，不因缺回执重跑模型或产生第二条回复 | 待核对真实幂等合同、读回与重试证据 | 未执行 |
| D3 | 提交成功，随后读取失败 | 不将读取失败误判为提交失败；不重发正文、不重跑模型；读取恢复后只显示原结果 | 待核对持久结果与显示层恢复边界 | 未执行 |
| D4 | 失败终态提交本身遇到断网/503 | 按现有策略恢复，恢复后明确失败终态；耗尽预算仍不可冒充成功或悄悄丢弃待恢复状态 | 待核对 fail 结算重试、预算和恢复出口；与普通提示消息区分 | 未执行 |
| D5 | 去卡重试仍被明确拒绝 | 不无限重试或另发消息冒充成功；进入失败收尾，诊断对应第二次实际提交内容 | 待核对二次拒绝、fail 路径及诊断脱敏 | 未执行 |

每行必须回答四个问题：

1. 模型是否被额外执行？次数和触发原因是什么？
2. 用户是否收到重复回复，或产生重复外部副作用？
3. 执行能否正确结束；尚未结束时是否明确处于可解释的待恢复状态？
4. 原有能力是否保留；若降级，损失与适用条件是否被准确记录？

**进入实验的条件：**每行补齐具体生产入口、已有测试标识、最小输入、预期、证据来源和运行方式。
协议是否支持幂等尚不明确时，先查协议，不盲目重试。没有新结果分支的项目复用已有用例。

## 4. 在固定条件下记录基线

按开工卡约定的次数运行同一案例，保留失败和中断结果，不只挑成功样本。具体命令在核对实际仓库和入口后填入记录，本文不预设未经验证的命令。

每次留一条可检查的轨迹：

| 运行编号/环节 | 时间或耗时 | 输入与状态摘要 | 动作/工具及回执 | 可观察结果与证据 | 下一步或停止原因 |
| --- | --- | --- | --- | --- | --- |
| 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |

轨迹记录可观察动作和状态，不要求采集模型隐藏推理；凭证、私人正文与敏感日志不进入公开报告或仓库。
计数、错误类别、脱敏标识与受控证据引用足够时，不复制完整内容。

达到预设预算、关键证据不可得、出现未授权副作用或结果不确定时，停止依赖该条件的实验并记录原因。
明确报告“未执行/受阻/未知”，不能用推测补出成功结果，也不能为了填表重复真实写入。

## 5. 分类失败，只改变一个因素

| 现象 | 优先检查 | 需要留下的依据 |
| --- | --- | --- |
| 理解错需求 | 输入、上下文范围和目标/实现方式是否混淆 | 原目标与实际产出的差异 |
| 一直查询、不交付 | 结束条件、缺证据的处理方式、预算 | 查询轨迹、重复查询及停止原因 |
| 工具失败后猜测成功 | 错误是否被读取、确定失败与未知是否区分 | 回执与最终表述的对应关系 |
| 重复执行/重复回复 | 进度保存、幂等标识、确认与恢复边界 | 模型执行次数、提交次数、实际保存/送达次数 |
| 并发后变慢 | 网络、工具耗时、排队及本机资源 | 分环节耗时；不直接归因于模型 |
| 测试通过但能力丢失 | 测试是否覆盖真实入口及原能力 | 用户场景、缺失能力和原有断言 |

每轮只选择一个优化因素，例如上下文范围、工具说明、流程拆分或某一恢复行为。
先写“假设 → 修改因素 → 预期改善 → 可能回退”，其余条件固定；不可避免的环境变化单独标注，不能当成优化收益。
涉及提醒强度、权限、过程归属、降级或配置负担时，重新对照原始目标及已有产品决定。

本步实际修改需在获准的实现阶段进行。先查现有用例，只对已确认的生产行为缺口做最小回归；修缺陷时保留旧版本失败、新版本通过的证据。

## 6. 同条件复验并比较

用同一案例集、初始状态和约定次数复验；记录版本、模型、配置、网络/资源差异及冷热缓存情况。
固定协议分支可复用确定性夹具；含真实模型的结果需报告波动，不以单次快慢断言优化有效。

| 指标 | 优化前 | 优化后 | 判定依据 |
| --- | --- | --- | --- |
| 结论正确且证据充分 | 待填，通过数/实际运行数 | 待填，通过数/实际运行数 | 由审阅人对照原问题及证据核对 |
| 原能力保留/降级准确 | 待填 | 待填 | 与开工卡逐项对应 |
| 失败恢复及重复副作用 | 待填 | 待填 | 各分支恢复结果、模型执行及实际写入/送达次数 |
| 总耗时与分环节耗时 | 待填 | 待填 | 同条件结果及范围；样本少时不报告不可靠的分位数 |
| 工具调用和人工纠正次数 | 待填 | 待填 | 按同一统计口径记录；重试另列 |
| 未执行、失败、受阻样本 | 待填 | 待填 | 保留原因，不计作通过 |

正确性、授权边界、去重及必须保留的能力优先于速度。少调工具、缩短输出或减少检查本身不算优化成功。
单测、组件夹具、集成验证和真实现场证据分别标明；不能用一个层级代替另一个。

## 7. 人工审阅与收口

审阅人按每行证据填写以下状态之一：**通过、失败、受阻、未执行、不适用（附理由）**。
不确定结果单独写明待核实内容，不能计为通过。审阅不要求自动创建其他 Agent 或额外任务。

整体结论分开记录：

- **完整验收通过**：本次适用的必要场景均通过，原始问题解决、必须保留的能力仍在，实际运行证据达到约定层级。
- **仅降级交付通过**：已确认的受限兜底达成，能力损失清楚；不得标为完整恢复。
- **未通过或证据不足**：列出失败/受阻/未执行项、影响、负责人及具体下一步，不以绿 CI、合并状态或评论清零替代验收。

最终记录模板：

```text
场景与原始目标：
基线/优化版本及运行环境：
必须保留的能力与已决定的取舍：
调用链、任务轨迹和证据位置：
失败分类与本轮唯一优化因素：
逐项验收结果及前后指标：
实际解决的问题：
降级、能力损失与未验证项：
整体结论及审阅人：
剩余事项、负责人、完成所需证据：
```

先人工重复跑通，再评估是否值得自动化。只有输入、判断口径、恢复与停止条件稳定，且重跑不会产生重复副作用时，才提出自动化方案；需另行确定执行电脑、账号、频率、预算和结果位置。
本文不创建定时任务、不要求新造框架、不跨仓修改服务端，也不授权提交、推送、合并或发布。

## 8. 从 #9398 落实到后续任务的执行步骤

以下步骤用于需要分阶段验收的工程任务，不将每次小改动都扩展为完整现场实验。

1. **开始时写一张当前状态卡。** 固定原始问题、必须保留的行为、版本来源与本轮范围；
   将场景标为“核心验收”“原现场补证”“补充风险”，每项写明分类依据。
   后两类不自动成为合并前置条件；是否阻塞按改动影响面、原需求和已有规则判断。
2. **先定证据，再运行。** 为每个核心判定写出最小失败输入和所需证据。
   瞬时闪现用受控延迟及连续录屏，最终状态用读回，后台执行次数用执行标识或日志；
   离散截图不能证明没有瞬时异常，可见回复数量不能证明后台执行次数。
   真实写入前先准备好录制和记录方式；录制方式及局限随结果保存。
3. **固定前后对照的来源。** 区分本轮实测、作者记录、独立审查及 CI 回执。
   未独立运行旧版时明确写出；合入主干、平台或模型变化须单列，不能归因于修复收益。
   PR head 变化后先复核差异，再决定哪些旧证据仍适用。
4. **给环境准备设置预算。** 在开工卡填准备时间／尝试次数上限、已有可用构建、目标机器和替代交付。
   环境失败先按日志分类，不重复启动同一失败路径；达到预算后交付已有证据和精确缺口，
   其余独立且获准的工作继续。不可跳过版本身份、安全或权限检查来制造可运行环境。
5. **在授权范围内连续完成。** 不为常规步骤反复等待“继续”；阶段更新说明新发现、下一步与停止条件。
   每次真实发送先确认上一轮结果；回执未知只核实、不重发。达到预定样本数后停止重复正常路径。
6. **失败与异常单独登记。** 保留首次失败、恢复动作和结果；新发现如输入状态未恢复，先登记为待核实，
   不能直接宣称新缺陷，也不能顺带扩大实现范围。持续失败的恢复场景优先在受控环境完成。
7. **结束时更新同一份记录。** 文首、验收矩阵和结论必须一致地呈现最新状态；
   历史经过明确标为历史，避免读者必须翻完追加章节才能知道完成情况。
   每个未完成项写明下一动作、所需证据、承接角色、是否已接手与是否影响当前结论。
8. **移交形成可执行包。** 包含版本核验、隔离前置条件、固定输入、预期、取证、停止条件和回填格式。
   准备说明不等于已分享、有人接手或已完成；发送、邀请、发布按用户授权执行。
   同时说明本机已完成部分和仍可完成部分，不把某个平台缺失说成全部工作都无法继续。

每次阶段交付使用以下简表；不填不适用的性能指标，不为填表重复真实写入：

| 项目 | 必填内容 |
| --- | --- |
| 当前结论 | 核心验收结果、原现场补证状态、已知局限 |
| 版本与来源 | 待验提交／构建、基线、环境差异、最后一次远端核验时间（未重查则注明） |
| 已完成 | 场景、实际结果、证据路径与来源层级 |
| 未完成 | 分类、下一动作、所需证据、承接角色、接手状态、阻塞依据 |
| 停止条件 | 样本预算、环境预算、未知副作用时如何核实 |
| 本轮改动 | 产品实现／验收文档／仅补证分别列明 |
